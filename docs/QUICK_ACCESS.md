# Quick access to messages while playing

Goal: a friend writes while you play → a native PS5 notification appears → you get to the right
conversation, read it, reply with the controller, and go back to your game, without sending the
payload through the loader again.

> **Hardware status:** proven on a PS5 with firmware 12.20 (Alpha 0.1, user report): native
> AKENO message notifications appear, also while a game is running. Everything new below is
> tested on Linux only; the button notification in particular is **unverified on hardware**.

## What Alpha 0.2 offers

| Way to the conversation | How | Status |
| --- | --- | --- |
| **Plain notification** (always) | `sceKernelSendNotificationRequest`, text "AKENO: <name>: <message>" | Proven on 12.20 (Alpha 0.1). Selecting it cannot open AKENO: the call has no action. |
| **Newest-message banner** | The AKENO page shows "New message from …  [Open] [Dismiss]" and puts the focus on **Open** when the page becomes visible again, unless you are typing | Linux/Chromium tested |
| **Start AKENO again** | Sending the ELF again does not start a second copy; the running app reopens its page **at the newest conversation you have not seen** (`#open=conversation:<id>`) | Linux tested; the reopen itself (browser launch) is proven on 12.20 |
| **Button notification** (experimental, opt-in) | `sceNotificationSend` with an "Open in AKENO" action (template of the SDK's `samples/notify`) whose URL is a one-time local link | **Unverified on hardware**; off by default |
| Drafts | A half-written reply survives incoming messages and re-renders | Linux/Chromium tested |

Use the controller: D-pad moves the focus, ✕ selects, ◯ (Escape) goes back. The on-screen
keyboard is the browser's own.

## The experimental button notification

`samples/notify` of the pinned SDK sends an `InteractiveToastTemplateB` toast with a `DeepLink`
action through `sceNotificationSend` (in `libSceNotification`). Whether the action can open a URL
in the web browser — and whether the call works from a payload on 12.20/13.60 at all — is not
documented anywhere. AKENO therefore treats it as an experiment:

- **Off by default.** Settings → Notifications → "Experimental: message notifications with an
  'Open in AKENO' button".
- **Never linked.** The SDK runtime refuses to start a payload whose `DT_NEEDED` library or any
  strong symbol does not resolve (`crt/rtld_payload.c`). Linking `libSceNotification` would have
  made the proven start-up depend on an unverified library. AKENO loads it with
  `dlopen("libSceNotification.sprx")` + `dlsym("sceNotificationSend")` (the SDK's
  `samples/hello_dlfcn` pattern) only when the switch is on.
- **Capability gate and fallback.** If loading fails (`unavailable`) or the system refuses the
  toast (`refused`), AKENO sends the proven plain notification instead, logs it once and counts
  it in Diagnostics. A linked symbol or accepted call does **not** prove the button works: only
  you can see that.
- **Controlled test.** Diagnostics → "Send a test notification with a button" sends one toast and
  reports the system's answer. Please report: does a toast appear, does it show a button, what
  happens when you select it (nothing / opens the browser / opens AKENO / something else).

### One-time links (security)

The button's URL ends up in the system's notification list, so it must not grant lasting access:

- It is `http://127.0.0.1:8642/t/<ticket>`: a random 128-bit ticket, **single use**, valid for
  **10 minutes**, at most 8 outstanding (the oldest is replaced).
- It never contains the device token or the page secret. Redeeming it returns a same-origin
  redirect to `/#t=<page secret>&open=<target>` — the same form AKENO itself uses when it opens
  the browser — so the secret only ever appears in the URL fragment of the local page.
- The page server listens on loopback only and checks the exact `Host` (DNS-rebinding defence)
  and `Origin`; a used, expired, malformed or unknown ticket gets a plain 403 page.
- Targets are generated by the console app from server events and validated against a fixed
  pattern (`messages`, `party`, `friends`, `games`, `invitations`, `conversation:<uuid>`) in C and
  again in the page; the server still decides whether this account may open that conversation
  (`GET /conversations/:id` is member-only).

## Why not a Control Center card, a PS-button shortcut or an overlay?

Investigated for this release; none has a safe, documented, repeatable mechanism available to a
payload:

| Idea | Finding | Decision |
| --- | --- | --- |
| Control Center card for AKENO | No API in the SDK; Control Center cards belong to the system UI (`SceShellUI`). Adding one would mean modifying or injecting into a system process. | Not done (safety rules) |
| Hijacking the PS button / a controller combo | Reading the pad in the background (`libScePad`, as in the secondary branch `claude/epic-bell-s1psav`) competes with the running game for the controller; no reviewed sample shows safe shared use, and a combo could be pressed in the game by accident. Remapping the PS button means hooking the system. | Not done; Branch B's pad code kept on its branch, unverified |
| Overlay drawn over the game | No documented way for a background payload to draw on screen; would need system hooks or video-out access. | Not done |
| Opening AKENO from the game | Possible only through the system: a notification action (experiment above) or switching to the web browser through the system's own app switcher if the browser stays open. | Experiment + documented |
| Native Game Base friends, presence, parties, voice, invites | No documented interface; would require impersonating PSN services or modifying system processes. | Unsupported; see [PS5_GAMEBASE_RESEARCH.md](PS5_GAMEBASE_RESEARCH.md) |

What the user can do today without any of these: keep the AKENO browser page open, switch to
the game, and come back to the browser with the system's own app switching (PS button) — the
banner then offers the newest message. Whether the PS5 keeps the browser page alive alongside a
running game is a hardware test item.

## Tests

`clients/ps5/tests/integration/run.mjs`: recent messages and `/api/inbox`; a second launch opens
the newest unseen conversation, and the default view once it was seen; button notifications carry
one-time links without the page secret; single use, expiry, malformed tickets, DNS rebinding;
plain fallback when the function is unavailable; in Chromium: the quick-open link, the banner,
drafts surviving incoming messages.
